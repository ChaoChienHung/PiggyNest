# Architecture

## Running application

The browser runs a React single-page application. `frontend/src/api/` wraps HTTP requests to the versioned FastAPI routes in `backend/app/api/v1/`. Authentication uses a bearer token. Each query for banks, transactions, categories, backup data, or statistics is scoped to the authenticated user.

The API uses SQLAlchemy sessions against SQLite by default. `backend/app/models/` defines the persisted schema, `backend/app/schemas/` defines request and response shapes, and `backend/app/domain/` holds reusable rules. Some endpoint modules still perform database orchestration directly; move a workflow into a service when it has multiple callers or needs more complex invariants. `backend/app/db/repositories/` currently covers only some resources. Avoid adding repository wrappers that merely repeat a one-line query.

`backend/app/domain/transactions.py` and `backend/app/domain/reports.py` are older CSV/pandas bookkeeping code; the FastAPI app does not route through them. `cli.py` is a separate development tool. Keep these paths distinct until there is a deliberate migration or removal.

## Transaction identity and transfers

Every transaction has a numeric `transactions.id`. A standalone transaction's logical `transaction_id` is `entry:<id>`. A **PiggyBank transfer** between two owned PiggyBanks creates **two** transactions in one database commit: a negative source transaction and a positive target transaction. Both have `type=transfer` and the same UUID in `transfer_group_id`, exposed as `transaction_id`. The transfer API also returns both numeric transaction IDs.

A **bank transfer** has one transaction because the other account is outside PiggyNest. `type=transfer_out` uses a negative amount; `type=transfer_in` uses a positive amount. Its `transfer_group_id` is null, and it is created, edited, or deleted by its numeric transaction ID. Bank transfers out count as spending and bank transfers in count as income in the current statistics policy; users can choose a category to describe their purpose.

Create a PiggyBank transfer only through `POST /api/v1/transfers`. The ordinary transaction endpoint rejects `type=transfer` while accepting `transfer_out` and `transfer_in`. A same-currency transfer has one positive `amount` and creates equal debit and credit amounts. A cross-currency transfer also requires a positive `received_amount` in the target currency; these are the actual amounts from the bank record, not amounts calculated from a fetched rate. The optional `date` is applied to both sides; without it, both sides use the current time. The frontend shows the implied rate as a check.

Fetch or edit any owned transaction with `GET` or `PUT /api/v1/transactions/{id}`. `GET /api/v1/transfers/{transaction_id}` returns both owned transfer legs for editing. For a same-currency PiggyBank transfer, editing one signed amount mirrors it to the other leg. For a cross-currency transfer, `amount` edits the selected leg and optional positive `counterpart_amount` edits the other leg, preserving each direction. Editing the note or date updates both legs in one commit. Transfer direction and directional categories are fixed. Delete either transaction through `DELETE /api/v1/transactions/{id}` and the backend deletes both in the same commit. Deleting either PiggyBank also removes both transactions.

Categories describe purpose, not money movement. `Transfer` is not a user category: bank transfers fall back to `Others`, and PiggyBank transfers carry system `Transfer In`/`Transfer Out` labels. `app/domain/category_names.py` maps old spellings (`Other`, `Transfer`, `Withdraw`, `Withdrawal`) to `Others` or `Withdrawals` wherever a category is written, including Excel import.

Older `type=transfer` transactions may lack `transfer_group_id`; some are historical PiggyBank transfers and others may represent bank transfers. `domain/transfer_links.py` identifies PiggyBank pairs only when amount, timestamp, source and target PiggyBank names, categories, and description agree uniquely. The [repair program](transfer-repair.md) audits them and can persist shared IDs. For an unresolved transaction, a person can explicitly link a reviewed debit and credit or mark it as a bank transfer. Until classified, editing or deleting that transaction, or deleting its PiggyBank, returns HTTP 409. Excel import rejects unclassified `type=transfer` transactions; run the repair before exporting data that will be imported elsewhere.

Balances sum signed integer minor units within a PiggyBank, then convert to the currency's major unit for the API. The current supported currencies (NTD and SGD) both have two decimal places. API and Excel import reject sub-cent values. Global income and spending statistics also accumulate integer minor units and exclude PiggyBank transfers, since moving funds between owned PiggyBanks does not change overall income or expense.

Each user has a display currency and optional fixed rates quoted as NTD per one unit of another currency. New accounts start with the owner-chosen `1 SGD = 24.00 NTD` rate; startup adds it to older accounts only if they have no saved SGD rate. `GET /api/v1/auth/me/rates` and `PUT /api/v1/auth/me/rates/{currency}` read and save only the authenticated user's rates, with an update time and at most four decimal places. Browser conversion goes through NTD when neither source nor display currency is NTD. A missing rate must be shown to the user instead of silently treating currencies as equal. The Dashboard and Reports fetch the signed transactions of selected PiggyBanks, convert each amount for display, and aggregate them by calendar period; PiggyBank transfer rows affect the balance but not income or spending. The older `/statistics` endpoint still returns native-currency aggregates and is not used for the combined Dashboard charts.

## Persistence and backup

The default database URL points to the repository's Git-ignored `data/piggynest.db`, independent of the API process's working directory. The API creates it on first startup. A fresh clone needs a newly registered test account. Automated tests override the URL and use an isolated SQLite database.

Excel export has bank, transaction, and category sheets. Import validates all rows, remaps IDs, then commits the account import atomically. Its `entry_id` records a row's original ID; `transaction_id` links the two sides of a transfer. Same-currency pairs must sum to zero; cross-currency pairs require one debit and one credit in banks with different currencies. An imported account receives fresh database IDs.

In older CSV files, `Transaction ID` can restart for each PiggyBank and year, so it identifies a source row only together with its PiggyBank and file. The source `Balance` is a per-file running total; PiggyNest calculates balances from signed imported amounts. The legacy importer keeps possible PiggyBank transfers in a local review report until their relationship is confirmed.

`app.main` currently calls `create_all` and applies local schema upgrades, including `transfer_group_id`, `token_version`, and the one-time `Float` to integer-minor-unit amount conversion. The amount upgrade rounds existing values to cents, verifies every row has an amount, and removes the old `amount` column. The Ludwig legacy importer separately normalizes known ChungHwaPost sub-cent Float residue smaller than one cent around whole NTD values before storage; the local audit report records affected entries. This local upgrade path is not a general migration system. Use versioned migrations before production schema changes.
